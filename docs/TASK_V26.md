## 1. アカウント切替で、取り込み中のポストが別のアカウントに保存される
### 原因
- `src/content/account.ts` の `setCurrentAccount()` が、先に `setAccountScope(新しい ID)` を呼び、そのあとで購読者に通知する。
- 通知を受けた `AutoCollector.onAccountChanged()` (`src/content/autocollect.ts`) は `pause('account')` を呼び、その中の `flush(true)` が `addCollected()` を呼ぶ。`addCollected()` は、モジュール内の `scope` (すでに新しいアカウント) に保存する。
- そのため、前のアカウントで集めた未保存の分 (最大 19 件) が、新しいアカウントの「未分類」に入る。

### 確認すること
- `addCollected` が `scope` を読む箇所と、`setCurrentAccount` の呼び出し順。

### 直し方
- `addCollected` に、保存先のアカウント ID を引数で渡せるようにする (`this.state.accountId` を渡す)。モジュール内の `scope` に頼らない。
- 取り込み中に使う、ほかの保存系の呼び出し (保存済み ID の読み込み、全文の要求、画像のキャッシュの要求) も、同じ理由で `state.accountId` を使っているか確認し、そろえる。
- アカウントが変わった時点で、保存先は変えない。続きの取り込みは、いまの動作どおり「一時停止」になり、ユーザーが押したときだけ再開する。

## 2. インポートの検証が足りない
### 原因
- `src/shared/storage.ts` の `validBookmark` が、`snapshot.handle`、`snapshot.author`、`snapshot.url` の中身、`media` の要素の型、`folderIds` の中身を見ていない。
- `handle` や `author` がないデータを読み込むと、`.toLowerCase()` などで管理画面が毎回落ちる。
- `snapshot.url`、`avatar`、`media` が `<a href>` / `<img src>` にそのまま使われる。`javascript:` のリンクや、任意のホストへの画像の要求が通る。
- `folderIds` が `[]` や `['all']` のポストが、そのまま入り、どのフォルダにも出ない。

### 確認すること
- `<a href>` と `<img src>` に使っている場所 (`safeHref` などの既存の関数を通っているか)。通っていない場所だけ直す。

### 直し方
- `validBookmark` で、`snapshot.handle` と `snapshot.author` が文字列であることを必須にする。満たさないポストは捨てる (いまの、不正なポストを捨てる動作と同じ)。
- `snapshot.url` は `https://x.com/` または `https://twitter.com/` で始まるものだけ通す。`media` と `avatar` は、`https:` の URL だけ通す。満たさない要素は捨てる (ポスト全体は捨てない)。
- インポートしたポストにも、保存時と同じ `normalizeFolderIds` を通し、`[]` / `all` を「未分類」に直す。
- 捨てた件数は、いまのインポート結果の表示に合わせる。新しい文言は増やさない。

## 3. 全文取得で、成功が失敗として数えられる
### 原因
- `src/background/fulltext.ts` の `fetchOne` が、`refresh()` の戻り値が `false` のとき `'fail'` を返す。
- `refresh` (`refreshFullText`) は、すでに更新済み、削除済み、すでにたたまれていない、のときも `false` を返す。
- 裏のタブ側の `updateFromStatusPage` (`src/content/fulltext.ts`) が先に更新すると、キュー側の `refresh` が `false` になり、失敗として数えられる。連続 3 件で `failures` により止まる。
- 停止ボタンの `aborted` による中断も、`'fail'` として数えられる。

### 確認すること
- `refreshFullText` の `false` になる条件をすべて挙げる。

### 直し方
- 「読めた (`r.ok`)」のあとの `refresh` が `false` でも、すでに全文が入っている (たたまれていない) か、ポストが無くなっているなら、失敗に数えない (`'ok'` または新しい `'skip'` として扱う)。本当に更新できなかった場合 (保存の失敗) だけ `'fail'`。
- `aborted` による中断は、失敗に数えない。
- 停止の直後に `enqueue()` された分が、黙って捨てられないようにする (停止が終わってから受け付ける)。

## 4. 「いま取得する」が、何もせずに完了する
### 原因
- `src/background/fulltext.ts` の `loop` が、`RETRY_MS` (1 時間) 以内に試した項目を飛ばし、それでも `done` を増やす。
- `recordTry` は取得の前に書く。一時的な失敗のあと、原因を直して「いま取得する」を押しても、すべて飛ばされて進捗が満ちる。何も取得されず、理由も出ない。

### 直し方
- 自動 (保存時のキュー) では、いまの 1 時間の再試行の間隔を保つ。
- 手動 (「いま取得する」) では、間隔を無視して取得する。ユーザーが明示的に押したため。ただし、間隔 (4〜8 秒)、上限 (50 件)、止める条件 (X の制限、連続 3 件の失敗) は、変えない。
- 自動でも、飛ばした項目は `done` に数えず、別に `skipped` として持つ。進捗の表示は、飛ばした件数を含めて矛盾しないようにする (新しい文言が要る場合は 8 言語に入れる)。

## 5. 自動取り込みが、`/i/history/likes` のタブで始まらない

- x.com 側の、ブックマーク一覧かどうかの判定関数 (`pageOk` など) を探し、同じ判定を管理画面側で使えるか。

- 開始の指示が、ページの条件で無視されたときは、ユーザーに分かる形にする。ただし新しい仕組みは作らず、既存のパネル / 帯の「案内」の枠に出す。文言は 8 言語に入れる。

## 6. 管理画面の外の速度: ボタンごとに全ポストを読み直している
### 原因

### 直し方

- 画面の動作は変えない。

## 7. 取り込みの保存が、全件を書き直している (O(n²))
### 原因
- `AutoCollector.seq` は、取り込み中に集めた全件 (スナップショットつき) を持ち、20 件のフラッシュのたびに `addCollected(this.seq, ...)` へ全件を渡す。`addCollected` は、全件を並べ直し (`assignOrder`)、保存データ全体を書き直す。上限なしの取り込み (最大 2 時間) では、件数の 2 乗に比例して重くなる。

### 確認すること
- `seq` を全件渡す理由 (一覧の並び順を保つため `assignOrder` が全体を見る)。順序の付け方を変えずに、差分だけで同じ結果になるか。

### 直し方
- フラッシュでは、前回のフラッシュ以降の新しい分と、その並び順に必要な最小限の情報 (直前の順序の値) だけを渡す。結果の並び順は、いまと同じにする。
- `seq` のうち保存済みの分は、ID だけ残してスナップショットを捨て、メモリを増やさない。
- 並び順が変わらないことを、テストで固定する (下記)。

### 直し方

## 9. `cachePostById` が、サービスワーカーのアカウントの範囲を入れ替えている
### 原因
- `src/shared/cacheops.ts` の `cachePostById` が、`setAccountScope(accountId)` で全体の範囲を入れ替え、`finally` で `prev` に戻す。途中に `await` があるため、別のアカウントの 2 件が近くに来ると、後から入れ替えた方の `prev` が古い値になり、範囲が戻らない。`getBookmark` が別のアカウントを読む。

### 直し方
- `refreshFullText` と同じく、`accountId` を引数で渡す形に統一する。`cachePostById` の内部から、全体の範囲の入れ替えをなくす。

## 10. ポップオーバーの、アカウント切替後の削除と二重表示

## 11. 一括操作の失敗が、利用者に伝わらない
### 原因
- `src/manager/App.tsx` が、一括操作を `void run(...)` で起動する。保存が失敗する (容量・保存のエラー) と、`run()` の Promise が拒否され、通知が出ず、`reload()` も呼ばれず、画面が古いまま残る。全体のエラー処理が「保存のエラー」の帯を出すが、原因と合わない。

### 直し方
- `run()` の中で `try/catch` し、失敗したら既存のトースト (または帯) に、既存のエラー文言 (`errStorage` など) を出す。失敗しても `reload()` は呼ぶ。
- 新しい文言は、既存で足りなければ 8 言語に入れる。

## 12. 取り込みの全文要求 (`truncatedIds`) のずれ
### 原因
- `src/content/autocollect.ts` で、`truncatedIds` は、ポストを数えた時点で埋まり、保存が成功した後に確定しない。最後のフラッシュが失敗しても ID が残り、保存されていないポストの全文を要求する。ページを再読み込みして続きから引き継ぐと (`adopt`)、それまでの分は空になり、全文の要求が出ない。

### 直し方
- 保存に成功したポストについてだけ、全文の要求の対象にする (`saved` に入れるのと同じ場所で確定する)。
- 引き継ぎの後でも、保存済みのたたまれたポスト (`truncated` が真) は、取り込みの終了時に拾えるようにする。最終的に、全文取得のキューは保存データの `truncated` を元にして作る (手動の `manualItems` と同じ関数を使ってよい)。

## 13. `Viewer` が、`media` が空だと落ちる
### 原因
- `src/manager/App.tsx` が `Math.min(viewer.index, media.length - 1)` を使い、`media` が空だと `-1` になる。`src/manager/Viewer.tsx` の `urls[-1]` が `undefined` になり、`viewerCandidates(undefined)` が例外を出して管理画面が落ちる。
- 画像を切り替えたとき、`attempt` / `failed` の初期化は効果 (`useEffect`) の中にあり、新しい画像の最初の描画は、前の画像の状態で行われる。失敗の表示が一瞬出る。

### 直し方
- `media` が空なら、ビューアを開かない (開く入口で止める)。念のため、`Viewer` の中でも空の場合は何も描かない。
- 状態は、画像の URL (または index) をキーにして持ち、切り替えの最初の描画から初期値になるようにする (`key` を付けて再生成する)。

## 14. ポップアップのフォルダ数が 1 多い

### 直し方

## 15. アイコンと色の `aria-label` が直書き
### 原因
