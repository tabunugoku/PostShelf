取り込みの流れと、取りこぼしが起きる場所

対象: 自動取り込み (src/content/autocollect.ts) と、あとから補う処理。コードの読み取りで作った図で、X の実際の描画順は実機未確認の推測を含みます。

1. 現在のロジック

① スクロール画面の高さの 0.8 倍ずつ。待ちは下限 0.4〜1.2 秒、上限 1〜4 秒。新しいポストが DOM に出れば、下限を過ぎた時点で次へ進む。
▼
② 読み取り readVisible → extractTweet画面にある article を 1 回だけ読み、すぐ seen に入れる (以後、同じ取り込みの中では読み直さない)。 読む項目: 本文・投稿者・アイコン (Tweet-User-Avatar img の src)・画像 (tweetPhoto img の src)・動画・リンク・引用。
▼
待ちの判定メディアが未読みか? (mediaPending) 「動画なのに poster が無い」または「画像リンク a[href*=/photo/] はあるのに img の src が空」のときだけ、保存を保留する。
アイコンは、この判定に入っていない。
保留なし ▼
取りこぼし A画像の枠 (写真リンク) がまだ DOM に無い、または img が無い状態で読むと、保留にならずメディアなしで保存される。
取りこぼし Bアイコンの img が未読み (src が空) でも、そのままアイコンなしで保存される。
保留あり ▼
mediaRetry に入れて、次のループ (次のスクロールのあと、約 1〜5 秒後) の読み取りで 1 回だけ読み直す。
取りこぼし C読み直しても空なら、そのまま (空のまま) 保存する。ポストが仮想化で DOM から消えていれば、最初に読んだ内容で保存する。
▼
③ 保存 addCollected20 件たまるごと、または一時停止・終了のときに保存。保存済みのポストは触らない (既存の判定は ID だけ)。
取りこぼし D「抜けたまま保存した」という印が、保存データに残らない。あとで、抜けを見つける手がかりがない。
▼
④ 全文の取得 (たたまれたポストだけ)終わったあと、裏のタブで個別ページを開き、本文だけを読む (refreshFullText は text / segments / translated しか更新しない)。1 回 30 件まで。
取りこぼし E同じページを開いているのに、そのページにあるアイコン・画像は読まずに捨てている。30 件を超えた分は、手動の「いま取得する」まで待つ。

2. あとから補う処理 (いまの実装)

画面にあるポストを見張るMutationObserver (src/content/index.ts) が、DOM の変化のたびに 300ms まとめて VisibleMediaBackfill を動かす。ブックマーク一覧・ホーム・個別ページのどれでも動く。
▼
補う条件 backfillMedia保存済みで、画面側にメディアがあり、保存側にメディアが無いときだけ。
項目元の投稿を開いたとき
画像 (media)補う (保存側が空のとき)
動画の印・poster補う
アイコン (avatar)補わない ← 今回の症状
投稿者名 (author。取れないと @ハンドルで代用される)補わない
投稿日時・リンクカード・引用元補わない
本文たたまれた (truncated) ポストだけ、全文を個別ページで更新

3. 取りこぼしの原因 (まとめ)

#原因どこ確度
A画像の枠が出る前に読むと、保留の条件に当たらず、メディアなしで保存されるsnapshot.ts の mediaPending高い (画像が抜ける症状と一致)
Bアイコンは未読みの判定が無い。src が空でも、そのまま保存されるsnapshot.ts の avatar高い (アイコンが抜ける症状と一致)
C読み直しは 1 回だけで、それでも空なら空のまま保存autocollect.ts の acceptMedia高い (コードから確定)
D抜けた状態の印が無いデータモデル確定
E裏のタブで個別ページを読むのに、本文しか使わないfulltext.ts / refreshFullText確定
F「あとから補う」がメディアだけで、アイコンなど他の項目に対応していないstorage.ts の backfillMedia確定 (今回の症状)

X が、写真の枠・img の src・アイコンの img を、どの順で、どれだけ遅れて DOM に出すかは未確認です。A・B が実際に起きている順序は、実機の診断 (後述の提案 4) で確かめるのが確実です。

4. 改善案 1: 取りこぼさない (取り込み側)

案 1-1「そろった」の判定を作る (isComplete) アイコン: img があり、src が空でなく、img.complete && naturalWidth > 0。
画像: 写真リンクの数と、img の数が同じで、すべて読み込み済み。動画: poster がある。
そろっていないポストは、保存しない (アイコンも判定に入れる)。
案 1-21 回の読み直しをやめて、待つ そろっていないポストは、そのポストの中の load イベントと DOM の変化で、そろうまで最大 3〜5 秒待つ。
待つ間も、スクロールは止めない (保留の件数に上限を付ける。ポストが DOM から消える前に、最後にもう 1 回読む)。
案 1-3待っても、そろわなかったとき: 印を付けて保存する 保存データに partial (抜けがあるかもしれない印) を付ける。印があるポストは、後述の「補う側」が必ず直し、直ったら印を消す。
「保存しない」ままにすると、ブックマークの一覧から消えて見える (取りこぼし以上に悪い) ので、保存はして印を付ける。
案 1-4スクロールの間隔を、そろうまで少しだけ延ばす X の読み込み中の判定 (timelineLoading) に、「画面のポストに、そろっていないものがある」を足す。速さは変えず、そろった時点で次へ進む。

5. 改善案 2: 取りこぼしたとき (補う側)

案 2-1「空の項目だけ埋める」の合流 (fillMissing) にそろえる backfillMedia を一般化する。保存側が空 (または無い) で、画面側に値があれば埋める。既にある値は、上書きしない (ユーザーが見ているものを壊さない)。
対象: avatar・media・videoPoster/hasVideo・author (@ハンドルのままのとき)・createdAt・hasLink・quote (保存側に無いとき、または引用の画像・アイコンが空のとき)。
案 2-2画面側も「そろってから」読む 補うときも、画面のポストが案 1-1 の「そろった」になってから使う。読み込み途中の空の値で、補えないまま終わらないようにする。
案 2-3個別ページを開いたときは、主役のポストを確実に補う updateFromStatusPage を、truncated のときだけでなく、保存済みの主役のポストなら必ず fillMissing する (全文の更新とは別にする)。
裏のタブの全文の取得 (readFullText) も、読んだ内容全体を返して、本文と一緒に fillMissing する (取りこぼし E の解消。新しい通信や権限は増えない)。
案 2-4表示側のアイコンの代用 (保存データを変えない) アイコンが空のポストは、同じ @ハンドルの別のポストのアイコンを、表示のときだけ借りる (アカウントの情報にあれば、それも)。
元の投稿を開かなくても、見た目はすぐ直る。アイコンの URL は変わることがあるが、表示の代用なので害は小さい。
案 2-5(要判断) partial のポストの、裏のタブでの自動修復 全文の取得と同じ仕組み (裏のタブ・間隔・上限・止める条件) で、partial のポストも開いて補う。ユーザーが元の投稿を開く手間が無くなるが、CLAUDE.md の「裏のタブで開く」例外の範囲を広げることになる。 ユーザーの判断が要る (私の推奨: まず 1-1〜2-4 を入れて、足りなければ検討)。
