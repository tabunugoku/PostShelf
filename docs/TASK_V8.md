### 括弧と疑問符の統一
文言中の補足括弧は、半角 `( )` ではなく全角 `（ ）` にそろえる。対象は `messages.json` の ja の全キー (例: `buttonModeSeparate`、`buttonModeReplace`、`dragHint`、`collectTitle` 周辺)。次のルールで直す。
1. 全角の疑問符 `？` の後ろの半角空白は残してよい (文を分ける用途)
2. 括弧の前の半角空白は削る (`ください (Alt で移動)` ではなく `（Alt で移動）`)
3. 括弧の中身を文にした方が読みやすい場合は、括弧をやめて文にする
4. 数字と `件` の間の半角空白 (`$COUNT$ 件`) は変えない

## B. ドキュメント
1. `docs/FAQ.md`
   - 「あなたが見ている画面の DOM だけです」→「表示中の画面の DOM だけです」
   - 「ご自身でスクロールしてください」→「自分でスクロールしてください」
   - 上限の説明を次のように 2 文に分ける。「X のブックマーク一覧には、表示件数の上限があるとされています。800〜1000 件程度と言われていますが、公式には確認できていません。」 (括弧をなくす)
   - 「スマホ」にそろえる (「モバイル」は使わない)
2. `README.md`
   - 「壊れたらそこだけ直す。」→「X の仕様変更で合わなくなったら、そこだけ直す。」
   - 「fixture テストは実際の X とのズレを保証しません。」→「fixture テストでは、実際の X との差異を検出できません。」
   - 「モバイル」を使っている箇所は「スマホ」にそろえる
3. 太字は、Markdown で太字として表示される書き方を保つ (太字の内側の先頭・末尾が記号で、外側が文字の場合は、`**` の外側に半角空白を入れる)

## C. 他の 7 言語への反映
A の `healthBroken`、`diagNotice`、`syncNativeDesc`、`confirmDelete` は、意味が変わるため、他の言語 (en, zh_CN, zh_TW, ko, es, pt_BR, fr) の同じキーも、同じ意味になるように直す。

1. `healthBroken`: 「送ってもらえると直せます」に当たる表現をやめ、「診断情報をコピーして GitHub で報告してください」の意味にする。自動送信と読めない書き方にする
2. `diagNotice`: 「個人情報は含まれません」に当たる断定をやめ、何が含まれて、何が含まれないかを具体的に書く (含まれない: ポストの本文、ユーザー名、URL / 含まれる: 拡張のバージョン、ブラウザの情報、表示言語、X の画面構造の骨組み)
3. `syncNativeDesc`: 「PostShelf がボタンを押す」と主語が分かる書き方にし、「X 標準のブックマーク」の語に統一する
4. `confirmDelete`: 「保存したポストは削除されない」の意味にする
5. 英語 (`en`) は、他の言語の基準になるので、先に直す。残りは AI 訳のままでよいが、`docs/I18N.md` の「ネイティブ校正が必要」の記述は維持する
6. キー一致テストが通ること (キー名とプレースホルダは変えない)

## D. 検証
1. `npm run typecheck`, `npm test`, `npm run build` がすべて通る (CI も成功)
2. A の全角括弧の統一で、文字列が変わるテスト (文言を直接比較しているもの) があれば、期待値を更新する
3. 変更は 1 コミットにまとめる
4. 最終報告: 直したキーの一覧、他の言語で意味を変えたキー、変えなかった判断とその理由
