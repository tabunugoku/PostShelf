## C. 手動インストールでも保存データを失わない仕組み
### C-1. 拡張機能 ID を固定する (最重要)
デベロッパーモードで読み込んだ拡張機能の ID は、通常は **読み込んだフォルダのパスから決まる**。フォルダを移動・改名したり、別の場所に展開し直したりすると ID が変わり、別の拡張機能として扱われて **保存データが引き継がれない** (実際に、ユーザーの環境で旧版と新版の ID が違っていた)。
1. `static/manifest.json` に `key` (公開鍵) を追加して、ID をパスに依存させない
   - RSA 2048 の鍵ペアを新しく作り、公開鍵だけを `key` に入れる (DER を base64 にした値)。秘密鍵は、手動インストールでは使わないので、リポジトリに入れない。捨ててよい
   - 作った鍵から求めた拡張機能 ID (a〜p の 32 文字) を `docs/INSTALL.md` と `docs/PUBLISH.md` に書き、ID の計算が合っていることをテストで確認する (公開鍵の SHA-256 の先頭 128 bit を、a〜p に変換する)
   - **この変更の副作用を `docs/INSTALL.md` に明記する**: `key` を入れた最初の版は、これまでの版とは ID が変わる。つまり、`key` 入りの版に切り替える 1 回だけは、旧版のデータが引き継がれない。切り替える前に、旧版で必ず「エクスポート」し、新版で「インポート」する手順を、画面つきで案内する。2 回目以降の更新では、ID が変わらないので、データは残る
2. `key` を入れても、権限・動作が変わらないことを確認する (必須の権限のテストが通る)

### C-2. 更新の手順を 1 つに決める
1. 推奨する手順を `docs/INSTALL.md` に書く
   - 拡張機能を入れる場所を **1 つのフォルダに固定** する (例: `C:\PostShelf`)。新しい版の zip を、そのフォルダの中身に **上書き展開** して、`chrome://extensions` で PostShelf の「再読み込み」(↻) を押す。削除はしない (削除するとデータも消える)
   - 更新の前に、設定の「データ」からエクスポートしておく (念のためのバックアップ)
2. 画面での支援
   - 設定画面の下部、または「データ」区画に、現在のバージョン (`chrome.runtime.getManifest().version`) を表示する。「更新するとき」の短い案内 (エクスポートしてから、同じフォルダに上書き) と、`docs/INSTALL.md` へのリンクを置く
   - バージョンが上がった直後の最初の起動のとき (保存してある前回のバージョンと比べる)、manager の上部に「PostShelf を更新しました (x.y.z)」と、閉じられるお知らせを 1 回だけ出す。外部への問い合わせはしない (新しい版が出ていることを、拡張機能が自分で調べることはしない。外部通信なしの方針)
3. 文言は 8 言語で追加する。ja は v8 / v10 / v12 の方針に従う

### C-3. パッケージ作成と品質確認
1. `npm run package`: `dist/` を検証してから、`release/postshelf-<version>.zip` を作る
   - zip の直下に `manifest.json` があること (展開したフォルダをそのまま「読み込む」ことができる)。ソースマップ、`.ts`、`node_modules`、テストを含めない
   - zip 作成用のライブラリを使う場合は devDependency にとどめ、拡張機能のバンドルには入れない。`release/` は `.gitignore` に入れる
2. `npm run release:check`: typecheck、テスト、ビルド、パッケージに加えて、次を機械的に確認する
   - manifest の version が `package.json` と一致している
   - 必須の `permissions` / `host_permissions` が現在の一覧と完全に同じ (増えていたら失敗)
   - 全 8 言語の `messages.json` のキーが完全に一致し、`$COUNT$` などのプレースホルダーも一致している
   - `dist` の JS に、外部のスクリプトの URL や `eval`、`new Function`、リモートコードの読み込みが含まれない
   - manifest が指すファイル (アイコンなど) がすべて zip に入っている
   - `key` から求めた拡張機能 ID が、`docs/INSTALL.md` に書いた ID と同じ
3. GitHub Actions に、タグ `v*` を push したときのワークフロー (`.github/workflows/release.yml`) を追加する: `release:check` を通し、タグと manifest の version が一致することを確認してから、zip を GitHub Release に添付する。CI の既存ワークフローは変えない
4. `THIRD_PARTY_NOTICES.md`: 同梱している第三者の部品 (Tabler Icons、Preact など) の名前、版、ライセンス全文を載せ、ビルドで `dist/` にも含める
5. 自分のコードのライセンス (`LICENSE`) は、**ユーザーの判断待ち** (他の人に配る場合だけ必要)。勝手に選ばず、`docs/PUBLISH.md` に選択肢 (MIT など) の違いを短く書くだけにする

### C-4. 品質の最終確認
1. 既存データを持つ状態での更新が安全であることを、移行テストで再確認する (v9 の移行、v11 の追加項目)
2. 初回インストール直後 (データなし) の画面が、空の状態として自然であること (案内文は「x.com の履歴の『ブックマーク』から取り込めます」)
3. エラーが出たときの表示 (ストレージの失敗、権限の拒否) が、`console` だけで終わらず画面に出ること。出ない箇所を洗い出して直す
4. `docs/MANUAL_TEST.md` に、リリース前の最終確認の一覧 (新しい Chrome のプロファイルでの初回インストール、`key` 入りの版への切り替え時のエクスポート/インポート、同じフォルダへの上書き更新で データが残ること、ライト/ダーク、サイドパネル、複数アカウント、画像のキャッシュ) を追加する

1. `docs/INSTALL.md` (日本語) と `docs/INSTALL.en.md` (英語): 手動インストールの手順書

   - うまくいかないとき (読み込みでエラー、アイコンが出ない、データが消えたように見える → ID が変わっていないか、`chrome://extensions` の ID と `docs/INSTALL.md` の ID を見比べる)
2. `docs/PUBLISH.md` を、この方針に合わせて書き直す。ストア公開の項目は削除せず、「いまは行わない (参考)」として末尾に分けて残す

   - 実機確認 (`docs/MANUAL_TEST.md`) を済ませてから、バージョンを `1.0.0` にする。それまでは `0.1.0` のまま
3. `README.md` に「インストール」節を足し、`docs/INSTALL.md` へ誘導する
