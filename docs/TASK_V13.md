## C. リリース準備 (Chrome Web Store 公開に向けて)
クラウドでできる範囲を実施する。ユーザーにしかできないこと (開発者アカウント、公開先の決定など) は D に分け、未決のものは勝手に決めず、プレースホルダーと「ユーザーの判断待ち」の印を付ける。

### C-1. バージョンとパッケージ
1. 公開時のバージョンは `1.0.0` にする。ただし、`docs/MANUAL_TEST.md` の実機確認が済むまでは変更しない (現在は `0.1.0` のまま。切り替えは `docs/PUBLISH.md` の手順にする)。`package.json` と `static/manifest.json` の version が一致していることを確認するテストを追加する
2. `npm run package`: `dist/` を検証してから、`release/postshelf-<version>.zip` を作る
   - zip の直下に `manifest.json` があること。ソースマップ、`.ts`、`node_modules`、テスト、ドキュメントを含めない
   - zip 作成用のライブラリを使う場合は devDependency にとどめ、拡張機能のバンドルには入れない
   - `release/` は `.gitignore` に入れる
3. `npm run release:check`: typecheck、テスト、ビルド、パッケージに加えて、次を機械的に確認する
   - manifest の version が `package.json` と一致、`description` が 132 文字以内 (全言語の `extDescription`)、`name` が `_locales` の `extName` と一致
   - 必須の `permissions` / `host_permissions` が現在の一覧と完全に同じ (増えていたら失敗)
   - 全 8 言語の `messages.json` のキーが完全に一致し、`$COUNT$` などのプレースホルダーも一致している
   - `dist` の JS に、外部のスクリプト (CDN) の URL や `eval`、`new Function`、リモートコードの読み込みが含まれない
   - アイコンの全サイズが存在し、manifest が指すファイルがすべて zip に入っている
4. GitHub Actions に、タグ `v*` を push したときのリリース用ワークフロー (`.github/workflows/release.yml`) を追加する: `release:check` を通し、タグと manifest の version が一致することを確認してから、zip を GitHub Release に添付する。CI の既存ワークフローは変えない

### C-2. ストア掲載用の文書 (`docs/store/`)
1. `docs/store/listing.ja.md` と `docs/store/listing.en.md`
   - 拡張機能名、短い説明 (132 文字以内)、詳しい説明、カテゴリ (候補: 仕事効率化)、単一の目的の説明
   - 詳しい説明の書き方: 何ができるか (フォルダ分け、名前・アイコン・色、リスト/ポスト/グリッド表示、画像と動画のサムネイル、複数アカウント、画像のキャッシュ)、データが端末内だけにあること、できないこと (モバイルアプリのブックマークの自動同期、動画の再生、端末間の同期) を正直に書く。誇張しない
   - 「X Corp. とは関係のない、非公式の拡張機能です」の一文を入れる。X のロゴや Twitter の旧ロゴ・青い鳥は使わない。「X」「x.com」は、対応するサービス名として説明に使うだけにとどめる
   - 画面の文言と掲載文で、機能の名前をそろえる
2. 他の 6 言語 (`zh_CN`, `zh_TW`, `ko`, `es`, `pt_BR`, `fr`): `docs/store/listing.<言語>.md` に、短い説明と詳しい説明の訳を置く。機械翻訳であることをファイルの先頭に明記する。**この 6 言語のストア掲載を行うかは、ユーザーの判断待ち** (最初は日本語と英語だけにする案もある)
3. `docs/store/permissions.md`: ストアの審査フォームに入れる説明を、権限ごとに書く
   - `storage` / `unlimitedStorage` (ブックマークとフォルダ、画像のキャッシュの保存)、`sidePanel`、host `x.com` / `twitter.com` (ボタンの挿入、画面の DOM の読み取り)、任意の権限 `pbs.twimg.com` (画像のキャッシュをオンにしたときだけ。画像の取得)
   - 「リモートコードを使っていない」の申告の根拠 (CDN なし、アイコンフォントを同梱)
   - データの扱いの回答案: 利用者のデータを収集・送信しない、第三者に売らない・譲渡しない、目的外に使わない。ブラウザの中 (端末内) だけで処理する。ストアのフォームの項目ごとの回答を表にする (フォームの項目名が実際と違う場合は、現在のフォームに合わせて直すこと。未確認の項目名は断定しない)
4. `docs/PRIVACY.md` (日本語) と `docs/PRIVACY.en.md` (英語): プライバシーポリシー
   - 収集するデータはない、端末内の `chrome.storage.local` / IndexedDB / 選んだフォルダにだけ保存する、外部のサーバーへ送らない、画像のキャッシュをオンにしたときだけ `pbs.twimg.com` から画像を取得する、診断情報は利用者が明示的にコピーして自分で報告するときだけ外に出る、削除する方法 (拡張機能の削除、設定の「すべてのデータを削除」)、問い合わせ先 (GitHub Issues の URL。`src/shared/links.ts` の `ISSUE_URL` と同じものを使う)、最終更新日
   - **この文書を公開する URL は、ユーザーの判断待ち** (リポジトリが非公開のままだと、GitHub 上では誰も読めない)。文書の中に URL は書かない
5. `docs/store/assets.md`: 画像の仕様と作り方 (下の C-3 の対応表)

## D. `docs/PUBLISH.md` の更新 (公開の手順書)
次の手順を、この順で書く。**ユーザーが行うこと**と、クラウド (または CI) が行うことを、項目ごとにはっきり分ける。
1. ユーザー: 実機確認 (`docs/MANUAL_TEST.md`) を全項目実施する。特に画像のキャッシュの 3 項目 (`pbs.twimg.com` の取得、フォルダ選択、再許可)、アカウント判定、`/i/history` の取り込み
