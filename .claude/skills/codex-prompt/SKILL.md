# Codex に渡すプロンプトを作る

作業の内容: `$ARGUMENTS`

## 手順

1. 作業の内容に関係するコードを読み、原因と直す場所を特定する (ファイル名と関数名まで)。分からないところは「推測」と書く。実機で確かめた事実と推測を分ける。
2. 作業の置き場所を決める:
   - まだ main にマージしていない作業の続きなら、そのブランチにコミットを足す。
   - 独立した作業なら、origin/main から `codex/<短い名前>` を切る。
3. 下のひな形でプロンプトを書き、1 つのコードブロックで渡す。地の文は日本語。項目は A, B, C... と英字で番号を振る (1 項目 1 コミット)。
4. コードブロックの後に「次の一手」を 1 行書く (例: 「このプロンプトを Codex に渡し、push が終わったら『状況を確認して』と送ってください」)。

## ひな形

```
<作業の 1 行の説明>。CLAUDE.md の「守ること」に従うこと。

【共通】
- <ブランチの指示: 「origin/main から新しいブランチ codex/xxx を作る」または「<branch> の続き。同じブランチにコミットを足す」>
- 1 項目 1 コミット。各コミットで npm run typecheck、npm test、npm run build が通ること (リリースに関わる変更なら npm run release:check も)。最後にまとめて push する。同じ原因で CI が 2 回失敗したら、そこで止めて報告する。
- main へのマージ、タグ、リリース、バージョン変更はしない。
- 保存データの形、必須の権限 (manifest)、外部通信は変えない。_locales の文言は足さない・変えない (文言を足す作業では、ここに足す文言を ja / en で明記する)。X の DOM のセレクタは src/shared/selectors.ts に集める。
- 各項目に、修正前のコードで失敗するテストを足す。x.com の DOM は test/fixtures に、架空のアカウント (@me、@sample_*) と架空の本文だけで作る。不確かな DOM の構造は fixture のコメントに前提を書く。
- 最後に、コミットごとのテスト結果、判断した点、実機で確認してほしい点を報告し、docs/MANUAL_TEST.md に v<次の番号> の節を足す。

【A. <項目名> (<実機で確認済み / 推測>)】
現象: <ユーザーが見たこと。画面の文言は実際の表示どおり>
原因: <ファイル・関数と、なぜそうなるか。推測なら「(推測)」>
直し方: <番号付きで、具体的に。変えないこと・守ることも書く>
テスト: <何を入力して何を確かめるか>

【B. ...】
```

## 守ること

- 決まっている方針を変える指示を入れない: AI 自動仕分けは見送り。自動取り込みは同意した開始だけ・速度を抑える・一時停止と停止ができる・X の制限で止まる、を広げない。全文の取得は裏のタブ (active:false)・4〜8 秒の間隔・上限・止める条件のまま。
- UI の文言は短く (ボタンは 10 文字ほど、1 行)、句の切れ目で改行する。文言の変更は、ユーザーが 1 件ずつ選んだものだけ。
- 実在のポスト、実在のアカウント名 (開発者自身のものも) をプロンプトに書かない。症状の説明に実在の URL が必要なときは、ID を伏せるか「実機の 2 件」のように書く。
- 1 つのプロンプトの項目は多くても 5〜6 個にする。それより多ければ分ける。
