# Codex に渡すプロンプトを作る

作業の内容: `$ARGUMENTS`

## 手順

1. 作業の内容に関係するコードを読み、原因と直す場所を特定する (ファイル名と関数名まで)。分からないところは「推測」と書く。実機で確かめた事実と推測を分ける。
2. 作業の置き場所を決める:
   - 独立した作業なら、origin/main から `codex/<短い名前>` の worktree を作る (`git worktree add ../PostShelf-wt/<短い名前> -b codex/<短い名前> origin/main`)。そこで `npm ci` をしておく。
   - まだ main にマージしていない作業の続きなら、そのブランチの worktree を使う。
3. 項目ごとに、触ってよいファイルを決める。項目の間で同じファイルを触らないように分ける (コミット計画を自動で当てるため)。分けられないときは、項目をまとめるか、別のプロンプトにする。
4. 下のひな形でプロンプトを書き、スクラッチパッドに `prompt-<短い名前>.md` として保存する。地の文は日本語。項目は A, B, C... と英字で番号を振る (1 項目 1 コミット)。文書の項目は `DOC` とする。
5. 受け入れ条件は、テストで確かめられる形で書く (「〜のとき、〜が 1 回だけ」「〜が前と同じ参照のまま」など)。競合・境界の観点には、重なった読み直し・途中で届く通知・空の配列・別のアカウントの同じ ID など、レビューで指摘されそうな場面を先に書く (プロンプトの外の指摘を減らすため)。
6. プロンプトを見せ、最後に「次の一手」を 1 行書く (例: 「Codex に渡して」と送ってください)。渡すときは `.claude/codex/run-codex-exec.sh <worktree> <プロンプト> <出力フォルダ>` を Bash の `run_in_background` で起動する。その後の流れ (コミット計画の適用、レビュー、後片付け) は CLAUDE.md の「Codex との分担」に従う。

## ひな形

```
<作業の 1 行の説明>。CLAUDE.md の「守ること」に従うこと。

【共通】
- いまの作業フォルダは worktree で、origin/main (<コミット>) から作ったブランチ codex/xxx にいる。ブランチは作り直さない。
- コミットと push はしない (.git はサンドボックスで書けない)。Opus が、最後の応答のコミット計画のとおりにコミットする。
- 各項目のあとで npm run typecheck、npm test、npm run build を実行し、通ること (リリースに関わる変更なら npm run release:check も)。
- main へのマージ、タグ、リリース、バージョン変更はしない。保存データの形、必須の権限 (manifest)、外部通信は変えない。_locales の文言は足さない・変えない (文言を足す作業では、ここに足す文言を ja / en で明記する)。X の DOM のセレクタは src/shared/selectors.ts に集める。
- 触ってよいファイル:
  - A: <ファイル> と、そのテスト
  - B: <ファイル> と、そのテスト
  - 文書: docs/MANUAL_TEST.md (v<前の番号> の節の直後に v<次の番号> の節「<題>」を足す。すべて実機未確認)
  - ほかのファイルは触らない。特に <変えてほしくないファイル> は変えない。
- 項目の間で同じファイルを触らない。
- 各項目に、修正前のコード (<コミット>) で失敗するテストを足す。テストのファイル名は機能が分かる英語の名前にし、先頭に `// 版: v<次の番号>` を書く。x.com の DOM は test/fixtures に、架空のアカウント (@me、@sample_*) と架空の本文だけで作る。不確かな DOM の構造は fixture のコメントに前提を書く。

【A. <項目名> (<実機で確認済み / コードで確認済み / 推測>)】
現象: <ユーザーが見たこと。画面の文言は実際の表示どおり>
原因: <ファイル・関数と、なぜそうなるか。推測なら「(推測)」>
直し方: <番号付きで、具体的に。変えないこと・守ることも書く>
受け入れ条件 (それぞれテストで確かめる):
- <条件>
競合・境界の観点 (プロンプトの外の指摘を減らすため、実装の前に確かめること):
- <場面>

【B. ...】

【最後に】
- 自分の差分を、上の受け入れ条件と競合・境界の観点で点検し、満たさない点があれば notes に書く。
- 最後の応答は、指定された JSON の形で返す:
  - items: 項目ごとに id ("A"・"B"・"DOC")、コミットのメッセージ (日本語。既存のコミットの書き方に合わせ、「管理画面: …」「x.com: …」「文書: MANUAL_TEST に v<次の番号> (…) の節を足す」の形)、その項目で変えたファイルの一覧 (新しいファイルとテストを含む)、修正前のコードでテストが失敗したか。
  - shared_files: 2 つ以上の項目が触ったファイル (無ければ空の配列)。
  - checks: typecheck・test・build の結果と、テストの件数の要約。
  - notes: 判断した点、点検で見つけた点。
  - manual_test: 実機で確かめてほしい点。
```

## 守ること

- 決まっている方針を変える指示を入れない: AI 自動仕分けは見送り。自動取り込みは同意した開始だけ・速度を抑える・一時停止と停止ができる・X の制限で止まる、を広げない。全文の取得は裏のタブ (active:false)・4〜8 秒の間隔・上限・止める条件のまま。
- UI の文言は短く (ボタンは 10 文字ほど、1 行)、句の切れ目で改行する。文言の変更は、ユーザーが 1 件ずつ選んだものだけ。
- 実在のポスト、実在のアカウント名 (開発者自身のものも) をプロンプトに書かない。症状の説明に実在の URL が必要なときは、ID を伏せるか「実機の 2 件」のように書く。
- 1 つのプロンプトの項目は多くても 5〜6 個にする。それより多ければ分ける。
